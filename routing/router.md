# 内容形态路由

> 用途：主会话在**确认点 1**（时长与语言）时，用它判定该用哪个渲染后端。
> 设计原则：**自动判定 + 可覆盖**。判定结果随确认点 1 一并告知用户，用户可否决。
> 判定不确定时一律回退 `remotion`（能力最成熟、有样片标尺）。

---

## 一、后端清单

| 后端 ID | 定位 | V1 状态 | 权威参考 |
|---|---|---|---|
| `remotion` | 黑底 MG 概念科普讲解（讲清 X 是什么 / 怎么运作） | ✅ 可用（从 anything2explainer 迁移） | `backends/remotion/reference/` |
| `manim` | 连续公式推导 / 证明 / 符号变形 | ✅ 可用（V1 最小闭环，样片留 V2） | `backends/manim/reference/` |
| `hyperframes` | 产品宣传 / 社交短视频 / PR walkthrough / HTML 原生动效 | ⏸ 未实现（回退 remotion） | `backends/hyperframes/README.md` |
| `terminal` | 真终端操作教学（安装 / 配置 / 命令执行） | ⏸ 未实现（V2 必做，真终端录制） | `backends/terminal/README.md` |

## 二、判据树（按顺序评估，取第一个命中的分支）

```text
输入：主题 + 时长 + 语言
```

### R1 → `manim`

**问：内容以「连续公式推导 / 证明 / 符号变形」为主体？**

判定信号（满足任意两条即命中）：

1. 解说词含 **≥3 个推导连接词**：由上式可得 / 代入 / 化简 / 因此 / 可得 / 整理后 / 移项 / 展开 / 配方 / 求导后
2. 用户明确说了：推导 / 证明 / 推导过程 / 一步一步算 / 公式变形 / 定理证明
3. 主题本身是"推某公式"：如"推导欧拉公式""证明中心极限定理""从定义推出梯度下降"
4. 画面主体预期是公式而非概念图示——即"每句话都在改屏幕上的数学式子"

**反信号（命中则不要走 manim）**：
- 讲的是"这个公式的直觉 / 意义 / 为什么长这样" → 这是概念片，走 `remotion`
- 只有 1–2 个公式，其余是类比和图示 → `remotion`
- 讲数学史 / 数学家的故事 → `remotion`

> **关键区分**：`manim` 的判据不是"题材是数学"，而是**"解说是否在连续操作符号"**。
> 「傅里叶变换在干什么」→ remotion（讲直觉）
> 「从傅里叶级数推出傅里叶变换」→ manim（连续推导）

### R2 → `hyperframes`（V1 未实现，回退 `remotion` 并告知）

**问：内容是「产品宣传 / 社交短视频 / PR walkthrough」？**

判定信号：
1. 用户明确提到产品名 / 版本号 / 发布 / 上线 / changelog / release notes
2. 时长倾向 <60 秒
3. 目标是"展示"而非"讲解"——需要品牌视觉、动效炫技、社媒比例（竖屏 9:16 等）

**V1 行为**：告知用户「这个题材更适合 hyperframes 后端，但 V1 还没实现；
先用 remotion 做，会按横屏 1280×720 出片，想要竖屏/强品牌视觉需要等 V3」。

### R3 → `terminal`（V1 未实现，回退 `remotion` + `CodeBlock` 并告知）

**问：内容是「命令行操作 / 环境搭建 / 敲代码教学」为主体？**

判定信号：
1. 主题是安装 / 配置 / 部署 / 环境搭建，且步骤必须真实执行可见
2. 用户明确要求"看到真实敲命令""看到终端输出""看到报错现场"
3. 内容主体是命令序列而非概念

**V1 行为**：告知用户「真终端录制后端 V2 才做；V1 用 remotion 的 `CodeBlock` 图元
做代码卡演示——能讲清概念和代码结构，但**不是真实执行的终端**。
如果你的片子必须有真实命令输出，建议等 V2 或改用 OBS 录屏后期配音」。

### R4 → `remotion`（兜底）

概念科普讲解：讲清楚 X 是什么 / 怎么运作 / 为什么重要。包括：
- 技术原理解析（RAG、Transformer、注意力机制）
- 数学/物理的**概念与直觉**（傅里叶在干什么、为什么电场线长这样、矩阵乘法为什么这么算）
- 工具/框架介绍
- 领域知识科普

## 三、主会话判定流程

```
1. 读用户主题
2. 按 R1 → R2 → R3 → R4 顺序过判据树
3. 得到 backend 与命中理由
4. 在确认点 1 一并输出：

   「想做多长？中文还是英文？
    这个主题我判定用「<后端中文名>」后端——<一句话理由>。
    如果你其实想要 <另一后端的风格>，告诉我，我换。」
5. 用户回复 → 采用用户指定（若有）或维持判定
```

### 覆盖优先级

| 优先级 | 来源 | 行为 |
|---|---|---|
| 1（最高） | 用户在请求里显式指定后端 | 直接采用，不再判定 |
| 2 | 用户在确认点 1 否决推荐 | 采用用户指定 |
| 3 | 自动判定 | 按判据树 |
| 4（最低） | 判定不确定 / 无信号 | `remotion` |

显式指定的写法（用户可能用）：
- `/video-craft manim 推导欧拉公式`
- 「用 Manim 做」
- 「这条要公式推导风格」

## 五、判定后必做

无论命中哪个后端，主会话都要：

1. **把后端 ID 写进解说词的注释行**（`script/narration.txt` 顶部）：
   ```
   # BACKEND manim
   ```
   这既是给后续 agent 的信号，也是 QC 时的核对点。

2. **按后端的阶段 3 分镜格式写分镜**——四个后端的分镜格式不同：
   - `remotion` → `backends/remotion/reference/narration-storyboard.md` 的镜头令牌
   - `manim` → `backends/manim/reference/storyboard.md` 的推导步格式
   - 其它后端未实现

3. **用对应后端的 `new_project` 建项目**——目录结构和配置文件不同。

## 六、给分类用的自检提示词

主会话拿不准时，用这三问自检：

1. **如果我暂停视频，观众下一步期待看到什么？**
   - 期待"屏幕上的式子被改写" → `manim`
   - 期待"看到一个新图示/动画揭示某个结构" → `remotion`
   - 期待"看到命令真的跑起来" → `terminal`
   - 期待"看到品牌动效/产品画面" → `hyperframes`

2. **把解说词里的所有具体名词删掉，剩下的动词是什么？**
   - 代入/化简/展开/移项/求导 → `manim`
   - 是什么/怎么运作/为什么/比如 → `remotion`
   - 安装/运行/输入/执行/配置 → `terminal`

3. **这条片子的"每个节拍"单位是什么？**
   - 一个推导步 → `manim`
   - 一个镜头（一句解说配一个画面） → `remotion`
   - 一条命令及其输出 → `terminal`
   - 一个宣传点 → `hyperframes`

三问里有**两问以上指向同一后端**，就用它。
